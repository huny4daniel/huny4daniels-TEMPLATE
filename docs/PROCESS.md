# 프로젝트 진행 절차 매뉴얼

백지 상태의 아이디어를 사람과 코딩 에이전트(Claude)가 **역할을 나눠 함께** 제품으로 만드는 표준 절차.
새로운 방법론이 아니라 업계에서 널리 쓰이는 관행을 순서대로 엮은 것이다.

| 출처가 되는 관행 | 이 문서에서 쓰이는 곳 |
|---|---|
| Product Owner / 개발팀 역할 분리 (Scrum) | 역할 분담 |
| Lean Canvas, 5 Whys, Jobs-to-be-Done | 1단계 아이디어 구체화 |
| PRD, 사용자 스토리, MoSCoW 우선순위 | 1단계 |
| Design Doc / RFC, C4 모델 | 2단계 |
| ADR (Michael Nygard 형식) | 2단계 이후 상시 |
| Walking Skeleton, 수직 슬라이스, MVP | 3단계 |
| Definition of Ready / Done | 3~4단계 |
| Explore → Plan → Code → Commit (Anthropic Claude Code 권장 워크플로) | 4단계 |
| TDD, 테스트 피라미드, CI, Trunk-based development | 4~5단계 |
| SemVer, Keep a Changelog | 6단계 |
| Runbook, Blameless Postmortem, KPT 회고 | 7단계 |

---

## 역할 분담

사람은 **무엇을, 왜**를 정하는 결정권자(Product Owner), Claude는 **절차를 이끌고 실행하는** 진행·실행 담당이다.
사람은 진행 순서를 기억하거나 챙길 필요가 없다. 다음에 무엇을 할지는 Claude가 매번 먼저 꺼낸다.

| | 사람 | Claude |
|---|---|---|
| 방향 | 아이디어 제공, 목표·우선순위 결정 | 질문으로 아이디어를 끌어내고 구조화 |
| 결정 | 선택지 중 선택, 승인/반려 | 선택지·트레이드오프·추천안 제시 |
| 문서 | 검토, 수정 지시 | 초안 작성, 갱신, 기록 |
| 구현 | 계획 승인, 결과 확인(실행·체감) | 계획, 코드, 테스트, 검증 |
| 외부 작업 | 계정·결제·비밀 값·기기 확인 등 사람만 가능한 일 | 필요한 시점에 구체적인 요청 |
| 진행 관리 | 신경 쓰지 않음 | 현재 단계 추적, 다음 행동 제안, 상태 기록 |

## 협업 규칙 (Claude가 지킨다)

### 1. 매 응답은 다음 행동으로 끝낸다

작업 결과를 보고한 뒤 반드시 아래 중 하나 이상으로 끝낸다. 사람이 "이제 뭐 하지?"를 고민하지 않게 하기 위함이다.

| 표시 | 의미 | 예 |
|---|---|---|
| **[질문]** | 진행에 필요한 정보 요청 | "주 사용자는 누구인가요? A / B / C (추천: B)" |
| **[제안]** | 다음에 할 일 제안 | "PRD 초안이 끝났습니다. 검토 후 2단계로 넘어갈까요?" |
| **[승인 요청]** | 게이트 통과·되돌리기 어려운 작업 전 확인 | "이 계획대로 구현을 시작할까요?" |
| **[요청]** | 사람만 할 수 있는 작업 | "GitHub 저장소 Secrets에 키를 등록해 주세요" |

### 2. 질문하는 방식

- 한 번에 **1~4개**, 가장 중요한 것부터 묻는다. 긴 설문지를 한꺼번에 던지지 않는다.
- 열린 질문만 던지지 말고 **선택지와 추천안**을 함께 준다. 선택지 UI(AskUserQuestion)를 쓸 수 있으면 사용한다.
- 사람이 "모르겠다", "알아서", "추천대로"라고 하면 추천안을 채택하고 **가정**으로 표시해 기록한 뒤 진행한다. 가정은 나중에 검증 대상이 된다.
- 이미 문서에 답이 있는 것은 묻지 않는다.

### 3. 사람 승인 없이 넘어가지 않는 지점 (게이트)

- 단계 전환
- PRD의 목표·비목표·MVP 범위 확정
- ADR 채택 (기술·구조 선택)
- 구현 계획 승인 (코드 작성 시작 전)
- 릴리즈, 원격 push, 외부 공개, 삭제 등 되돌리기 어려운 작업

이 외(읽기, 초안 작성, 승인된 계획 범위 안의 구현, 테스트 실행, 문서 기록)는 묻지 않고 진행한다.

### 4. 기록 규칙

| 무엇을 | 어디에 | 언제 |
|---|---|---|
| 현재 단계, 다음 할 일, 사람 대기 항목 | `docs/STATUS.md` | 단계·작업 전환 시, 세션 종료 시 |
| 제품·범위 결정 (기술 외) | `docs/STATUS.md` 결정 기록 | 결정 직후 |
| 기술·구조 결정 | `docs/adr/` | 결정 직후 |
| 작업별 계획과 진행 경과 | `docs/plans/<이슈>-<이름>.md` | 계획 시, 단계 완료마다 |
| 사용자에게 보이는 변경 | `CHANGELOG.md` `[Unreleased]` | 커밋 시 |
| 반복된 실수, 환경 함정 | `AGENTS.md` Gotchas | 발견 즉시 |

### 5. 세션 운영

- **시작**: `docs/STATUS.md`(CLAUDE.md가 자동으로 불러옴)와 진행 중인 계획 문서를 확인하고 한두 줄로 브리핑한다.
  "현재 3단계, 이슈 #4 계획 승인 대기 중입니다. [승인 요청] …"
- **진행 중**: 계획 문서의 체크박스와 진행 기록을 갱신한다.
- **전환·종료**: 작업 단위가 끝나거나 사람이 마무리를 원하면 `/wrap`으로 상태를 기록하고 커밋을 제안한다. 이후 `/clear`해도 다음 세션이 STATUS.md로 이어받는다.

### 6. 명령어

| 명령 | 용도 |
|---|---|
| `/kickoff [아이디어]` | 새 프로젝트 시작. 0단계 점검 후 1단계 인터뷰 시작 |
| `/next` | 현재 상태를 파악해 다음 행동 제안 (언제든 "이어서 하자"와 같음) |
| `/plan <이슈>` | 구현 계획 작성 |
| `/adr <주제>` | 결정 기록 작성 |
| `/review` | 변경 사항을 Definition of Done 기준으로 점검 |
| `/fix <이슈 또는 증상>` | 버그 분류 후 수정 루프 진행 (유지보수 모드) |
| `/wrap` | 세션 마무리: 상태·진행 기록 갱신, 커밋 제안 |
| `/adopt [템플릿 경로]` | 이미 진행 중인 프로젝트에 이 구조·절차를 도입 |

## 전체 흐름

```
0 초기화 → 1 아이디어 구체화·PRD → 2 설계 → 3 계획 → [4 구현 ⇄ 5 검증] → 6 릴리즈 → 7 운영·회고
             ↑ 큰 새 기능                          ↑_______ 다음 마일스톤 ________________|
             |                                                                          |
             |____________________ 유지보수 모드 (버그 분류 → 수정 → PATCH 릴리즈) ←______|
```

- 0~2단계는 처음 한 번, 3~7단계는 마일스톤마다 반복한다 (반복 개발).
- 첫 릴리즈 이후에는 **개발 모드**(3~7 반복)와 **유지보수 모드**(버그 수정 루프)를 오간다. 현재 모드는 STATUS.md에 기록한다.
- 끝은 따로 정하지 않는다. 더 진행하지 않기로 하면 "프로젝트 종료" 절차로 보관한다.

| 단계 | 산출물 | 템플릿 |
|---|---|---|
| 0 초기화 | 저장소, STATUS.md | — |
| 1 아이디어 구체화·PRD | `docs/product/idea-brief.md`, `docs/product/PRD.md` | `templates/idea-brief.md`, `templates/prd.md` |
| 2 설계 | `docs/architecture/overview.md`, ADR | `templates/design-doc.md`, `templates/adr.md` |
| 3 계획 | 마일스톤, GitHub 이슈, 첫 작업 계획 | `templates/plan.md` |
| 4 구현 | 코드, 테스트, 커밋, 진행 기록 | `templates/plan.md` |
| 5 검증 | CI 통과, 사람 확인 결과 | PR 템플릿 |
| 6 릴리즈 | 태그, CHANGELOG, 배포물 | `templates/release-checklist.md` |
| 7 운영·회고 | Runbook, Postmortem, 회고 | `templates/runbook.md`, `templates/postmortem.md`, `templates/retrospective.md` |

작은 프로젝트는 문서를 짧게 쓰되 단계를 건너뛰지는 않는다.

| Claude | 사람 |
|---|---|
| 자리표시자·STATUS.md 상태 점검, 프로젝트 이름 확인 | 저장소 생성(템플릿 사용), 원격 연결 |

## 1단계: 아이디어 구체화 → PRD

목적: 막연한 아이디어를 **누구의 어떤 문제를 어떻게 푸는지**가 분명한 요구사항으로 만든다. 어떻게 구현할지는 아직 다루지 않는다.

### 1-1. 아이디어 브리프 (Lean Canvas 기반 인터뷰)

Claude는 먼저 사람이 준 설명(프롬프트, 첨부 문서)에서 아래 항목을 최대한 추출해 `docs/product/idea-brief.md`를 채우고, **비어 있거나 모호한 항목만** 아래 순서로 한 주제씩 질문한다.

- 설명이 충분하면 인터뷰 없이 채운 브리프를 요약해 보여주고 확인만 받은 뒤 1-2로 넘어간다.
- 설명이 한 줄뿐이면 처음부터 인터뷰한다.
- 어느 경우든 브리프 문서는 만든다. 이후 단계가 이 문서를 기준으로 삼기 때문이다.

1. **문제** — 어떤 상황에서 무엇이 불편한가? 답이 해결책 형태("~하는 앱")로 나오면 **5 Whys**로 그 밑의 문제를 찾는다.
2. **사용자** — 누가 그 문제를 가장 절실하게 겪는가? (얼리어답터 한 부류로 좁힌다)
3. **현재 대안** — 지금은 어떻게 해결하고 있고, 무엇이 부족한가?
4. **해야 할 일(JTBD)** — "~할 때, ~하고 싶다, 그래야 ~할 수 있다" 형식으로 정리
5. **가치 제안** — 기존 대안 대비 한 문장으로 말하는 차별점
6. **해결책 핵심 기능** — 가치 제안을 증명하는 최소 기능 3개 이내
7. **성공 지표** — 잘 되고 있다는 것을 무엇으로 알 수 있는가?
8. **제약** — 일정, 플랫폼, 비용, 사용할 수 있는 기술

사람이 답을 모르면 Claude가 2~3개 후보와 추천안을 제시하고, 고른 것은 **가정**으로 표시한다.
주제마다 답을 들으면 브리프를 갱신하고, 마지막에 브리프 전체를 요약해 보여준다.

### 1-2. PRD

1. Claude가 브리프에서 PRD 초안을 만든다: 목표/비목표, 사용자 스토리, 기능 요구사항(MoSCoW), 수용 기준, 비기능 요구사항, 마일스톤 초안.
2. 비어 있거나 모호한 항목만 추가로 질문한다.
3. 사람이 검토하고 목표·비목표·MVP 범위(Must)를 확정한다.

**게이트 [승인 요청]**: Must 항목만으로 MVP 범위가 명확하고, 비목표가 적혀 있으며, 사람이 승인했다.

## 2단계: 설계

| Claude | 사람 |
|---|---|
| 기술·구조 대안 2~3개와 트레이드오프, 추천안 제시 | 선택 |
| 설계 문서·ADR 작성, 자리표시자(명령어) 채우기 | 검토·승인 |

1. Claude가 결정이 필요한 항목 목록을 먼저 보여준다 (언어·프레임워크, 저장 방식, 배포 형태, 대상 플랫폼 등).
2. 항목별로 대안 비교 → 사람 선택 → ADR 작성을 반복한다.
3. `docs/architecture/overview.md` 작성: 시스템 컨텍스트, 구성 요소(= apps/packages 분할), 데이터 모델, 주요 흐름. 다이어그램은 C4의 Context / Container 수준(Mermaid)이면 충분하다.
4. 모노레포 분할 원칙
   - 배포 단위 = `apps/` 하나.
   - 두 곳 이상에서 쓰면 `packages/`로 승격. 처음부터 쪼개지 않는다 (YAGNI).
   - 의존 방향은 `apps → packages`만 허용.
5. 스택이 정해지면 AGENTS.md의 명령어 표와 워크스페이스 설정을 채운다.

**게이트 [승인 요청]**: 첫 구현에 필요한 기술 선택이 모두 ADR로 남았고, 설계 문서를 사람이 승인했다.

## 3단계: 계획

| Claude | 사람 |
|---|---|
| 마일스톤·이슈 분해 초안 | 우선순위 조정, 승인 |
| 승인 후 GitHub 마일스톤·이슈 생성 | — |

1. 첫 마일스톤은 **Walking Skeleton**: 모든 계층(UI → 로직 → 저장 → 빌드 → 배포)을 최소 기능으로 관통하는 실행 가능한 뼈대. CI와 release 워크플로도 이때 붙인다.
2. 이후 마일스톤은 **수직 슬라이스**(사용자가 체감하는 기능 하나를 끝까지)로 나눈다.
3. 이슈 하나 = PR 하나 = 세션 하나 정도의 크기로 맞추고, 각 이슈에 수용 기준을 적는다.

**Definition of Ready (착수 가능 조건)**
- [ ] 수용 기준이 검증 가능한 문장으로 적혀 있다
- [ ] 의존하는 결정(ADR)이 끝났다
- [ ] 한 세션(수 시간) 안에 끝낼 크기다

**게이트 [승인 요청]**: 마일스톤 순서와 첫 마일스톤의 이슈 목록을 사람이 승인했다.

## 4단계: 구현 (이슈마다 반복)

```
Explore → Plan → [승인] → Code → Verify → Commit → 기록
```

1. **다음 이슈 선택** — 현재 마일스톤의 열린 이슈 중 의존성이 풀린 것, 번호 순. Claude가 제안하고 사람이 확인한다.
2. **Explore** — 관련 문서·코드를 읽기만 한다.
3. **Plan** — `docs/plans/<이슈>-<이름>.md` 작성 → **[승인 요청]**. 승인 전에는 코드를 쓰지 않는다.
4. **Code** — 계획 단위로 구현. 테스트 가능한 로직은 TDD(실패하는 테스트 → 구현 → 통과).
5. **Verify** — 테스트·린트·타입 체크·빌드 실행. 사람이 직접 봐야 하는 부분은 **[요청]**으로 확인 방법을 구체적으로 안내한다.
6. **Commit** — 논리 단위로 커밋, CHANGELOG 갱신, PR 생성 제안.
7. **기록** — 계획 문서 진행 기록, STATUS.md 갱신 → 다음 이슈 **[제안]**.

계획에 없던 결정이 필요해지면 멈추고 **[질문]**한다. 방향이 틀어지면 덧칠하지 않고 되돌린 뒤 계획을 고친다.

**Definition of Done (완료 조건)**
- [ ] 수용 기준을 모두 만족
- [ ] 테스트 추가/수정, 전체 테스트 통과
- [ ] 린트·타입 체크·빌드 통과
- [ ] 필요한 문서(ADR, README, CHANGELOG) 갱신
- [ ] 리뷰(`/review` 또는 사람) 완료

---

## 5단계: 검증

- **테스트 피라미드**: 단위 테스트 다수 > 통합 테스트 일부 > E2E/수동 소수.
- **CI**: PR마다 설치 → 린트 → 타입 체크 → 테스트 → 빌드. 실패한 PR은 병합하지 않는다.
- **리뷰**: 작성한 세션과 다른 세션에서 `/review`를 돌리면 더 객관적이다.
- **사람 확인**: 마일스톤 끝에 Claude가 확인할 시나리오 목록을 만들어 **[요청]**하고, 결과를 기록한다.

**게이트 [승인 요청]**: 마일스톤의 모든 이슈가 DoD를 만족하고 사람 확인을 마쳤다.

---

## 6단계: 릴리즈

1. Claude가 `templates/release-checklist.md`로 점검하고 버전을 제안한다 (SemVer: 호환 깨짐 MAJOR / 기능 추가 MINOR / 수정 PATCH, 1.0.0 전에는 MINOR로 호환 깨짐 허용).
2. CHANGELOG `[Unreleased]` → `[X.Y.Z] - 날짜`.
3. **[승인 요청]** 후 커밋 → `git tag vX.Y.Z` → 커밋과 태그 함께 push → release 워크플로 결과 확인.
4. **[요청]** 배포물을 실제 설치해 확인.

---

## 7단계: 운영·회고

- **회고**: 마일스톤이 끝나면 Claude가 KPT(Keep / Problem / Try) 질문을 던지고 `docs/retros/`에 기록한다. Try 항목은 AGENTS.md, 이 문서, 템플릿에 반영을 제안한다.
- **Runbook**: 배포·롤백·자주 생기는 문제 대응을 `docs/runbooks/`에 둔다.
- **Postmortem**: 사용자 영향이 있던 문제는 비난 없는(Blameless) 형식으로 기록한다.
- 이후 Claude가 다음 방향을 [제안]하고 사람이 고른다:
  - 다음 마일스톤이 있으면 **3단계** (새로운 큰 기능이면 **1단계** PRD 갱신부터)
  - 계획된 기능이 없고 버그·소소한 개선이 중심이면 **유지보수 모드**

---

## 유지보수 모드 (버그 처리)

첫 릴리즈 이후 오류 수정이 주된 일이 되면 이 모드로 진행한다. 이슈 트리아지, 회귀 테스트, 핫픽스 같은 일반적인 유지보수 관행을 따른다.

### 1. 트리아지 (분류)

새 이슈나 버그 제보가 들어오면 Claude가 다음을 하고 사람은 우선순위만 승인한다.

1. 재현 시도 → 재현 절차·환경을 이슈에 정리. 재현되지 않으면 필요한 정보를 [요청]한다.
2. 분류: 버그(`bug`) / 기능 요청(`enhancement`) / 질문·중복·의도된 동작(닫기 제안)
3. 우선순위 제안:

| 라벨 | 기준 | 처리 |
|---|---|---|
| `P0` | 실행 불가, 데이터 손실, 보안 문제, 대부분의 사용자 영향 | 진행 중 작업을 멈추고 즉시 수정 → 핫픽스 릴리즈 |
| `P1` | 주요 기능 장애, 우회 방법이 어려움 | 다음 작업으로 수정 |
| `P2` | 일부 기능 문제, 우회 가능 | 모아서 처리 |
| `P3` | 표시·문구 등 사소한 문제 | 여유 있을 때 |

기능 요청은 바로 구현하지 않고 PRD 백로그에 모았다가 개발 모드(1 또는 3단계)에서 다룬다.

### 2. 수정 루프

```
재현 → 실패하는 테스트 → 원인 분석 → 수정 → 검증 → 커밋 → 기록
```

1. **재현**: 증상을 확실히 재현한다.
2. **실패하는 테스트(회귀 테스트)**: 버그를 재현하는 자동 테스트를 먼저 만든다. 자동화가 어려운 경우(UI 등)는 수동 확인 절차를 이슈에 적는다.
3. **원인 분석**: 증상이 아니라 근본 원인을 찾는다. 같은 원인의 다른 증상이 있는지도 확인한다.
4. **수정**: 원인만 고친다. 관련 없는 리팩터링을 섞지 않는다.
   - 작은 버그: 계획 문서 없이 진행하고, 원인과 수정 내용을 이슈 댓글·커밋에 남긴다.
   - 수정 범위가 크거나 구조적 원인: 4단계처럼 `docs/plans/`에 계획을 쓰고 [승인 요청]한다. 구조 변경이면 ADR도 쓴다.
5. **검증**: 새 테스트와 전체 테스트·린트·빌드 통과. 사람이 확인해야 하면 확인 방법을 [요청]한다.
6. **커밋·기록**: CHANGELOG `[Unreleased]`의 `Fixed`에 기록, 이슈 종료, STATUS.md 갱신.

### 3. 릴리즈

- **P0**: 수정 즉시 PATCH 릴리즈(핫픽스). 사용자 영향이 있었으면 Postmortem을 쓴다.
- **P1~P3**: 수정이 몇 개 모이거나 일정 기간이 지나면 Claude가 PATCH 릴리즈를 [제안]한다. 6단계 체크리스트를 그대로 쓴다.

### 4. 모드 전환

- 유지보수 모드에서 `/next`는 열린 버그를 P0 → P3, 같은 등급은 오래된 순으로 제안한다.
- 기능 요청이 쌓이거나 열린 P0·P1이 없으면 Claude가 개발 모드(새 마일스톤, 3단계) 전환을 [제안]한다.

## 프로젝트 종료 (선택)

더 이상 진행하지 않기로 하면:

1. README 상단에 상태(유지보수 중단, 보관됨)와 마지막 버전을 적는다.
2. STATUS.md 단계를 "종료"로 바꾸고 마지막 회고를 남긴다.
3. 열린 이슈를 정리(닫기 또는 라벨)하고 GitHub 저장소를 Archive 처리한다 ([요청] — 사람이 결정).

---

## 기존 프로젝트에 도입

이미 진행 중인 프로젝트에는 템플릿을 덮어쓰지 않고 단계적으로 도입한다. `/adopt` 명령으로 진행한다.

1. **비침습 추가** — 문서·에이전트 설정·이슈/PR 템플릿만 추가한다. 이미 있는 파일(CLAUDE.md, README, .gitignore, CI, release.yml)은 덮어쓰지 않고 필요한 부분만 합친다.
2. **역방향 문서화** — 코드에서 현재 상태를 읽어 문서를 만든다. Claude가 초안을 쓰고 사람은 확인만 한다.
   - `docs/architecture/overview.md`: 현재 구조
   - `docs/adr/`: 이미 내린 주요 결정을 사후 기록 (상태 Accepted, 맥락에 "사후 기록"이라고 명시)
   - `docs/product/PRD.md`: 현재 기능 목록 중심의 간단한 버전. 목표·비목표는 사람이 확인
   - `AGENTS.md`: 실제 명령어·스택으로 자리표시자 채우기
3. **현재 위치 결정** — STATUS.md에 단계와 모드를 정한다. 대개 4단계(개발 중) 또는 유지보수 모드다. 0~2단계는 역방향 문서로 완료 처리한다.
4. **폴더 구조는 옮기지 않는다** — 기존 코드를 `apps/`로 옮기는 것은 빌드·릴리즈 경로를 바꾸는 위험한 작업이다. 앱이 둘 이상이 되거나 공유 코드가 생길 때 ADR을 쓰고 별도 작업으로 `git mv`(이력 보존)해 옮긴 뒤 빌드·릴리즈를 검증한다.

## 스택별 모노레포 도구 (표준 선택지)

| 스택 | 워크스페이스 | 태스크 러너 |
|---|---|---|
| JavaScript/TypeScript | pnpm workspaces (`pnpm-workspace.yaml`) | Turborepo 또는 Nx |
| Python | uv workspaces (루트 `pyproject.toml`의 `[tool.uv.workspace]`) | `uv run`, Makefile/justfile |
| Android/Kotlin/JVM | Gradle 멀티 프로젝트 (`settings.gradle.kts`) | Gradle |
| 혼합 | 언어별 워크스페이스를 각 앱 폴더에 두고 | 루트 Makefile/justfile로 통합 |

단일 앱 프로젝트도 같은 구조를 쓴다 (`apps/` 하나, `packages/` 비어 있음).
