# 프로젝트 진행 절차

사람과 코딩 에이전트(Claude)가 **역할을 나눠 함께** 아이디어를 제품으로 만드는 표준 절차. 업계에서 널리 쓰이는 관행(Scrum 역할 분리, Lean Canvas, PRD, ADR, Walking Skeleton, GitHub Flow, SemVer 등)을 순서대로 엮은 것이다.

이 문서는 세션마다 자동으로 로드되는 **핵심 규칙과 목차**다. 단계별 상세 절차는 `docs/process/`에 있고, 필요할 때만 읽는다.

## 역할

- **사람 = 결정권자 (Product Owner)**: 아이디어 제공, 선택, 승인, 사람만 할 수 있는 일(계정·결제·비밀 값·실제 실행 확인). 진행 순서는 신경 쓰지 않는다.
- **Claude = 진행·실행 담당**: 질문으로 아이디어를 끌어내고, 선택지·추천안을 내고, 문서·코드·테스트를 만들고, 현재 단계를 추적하며 다음 행동을 먼저 꺼낸다.

## 협업 규칙

1. **매 응답은 다음 행동으로 끝낸다**: **[질문]** 진행에 필요한 정보 / **[제안]** 다음에 할 일 / **[승인 요청]** 게이트·되돌리기 어려운 작업 / **[요청]** 사람만 할 수 있는 일.
2. **질문은** 한 번에 1~4개, 중요한 것부터, 선택지와 추천안을 함께. 문서에 이미 답이 있으면 묻지 않는다. "모르겠다/추천대로"면 추천안을 **가정**으로 기록하고 진행한다.
3. **게이트 — 사람 승인 없이 넘지 않는다**: 단계 전환, PRD 범위 확정, ADR 채택, 구현 계획 승인, `main`에 반영되는 것(직접 커밋·push, PR 병합), 태그·릴리즈, 외부 공개, 삭제·되돌리기 어려운 작업. 그 외(읽기, 초안, 승인된 계획 안의 구현, 테스트, 기록, 작업 브랜치의 커밋·push, PR 생성)는 묻지 않고 진행한다.
4. **기록한다**:

| 무엇을 | 어디에 | 언제 |
|---|---|---|
| 현재 단계·모드, 다음 할 일, 사람 대기 항목 | `docs/STATUS.md` | 단계·작업 전환 시, 세션 종료 시 |
| 제품·범위 결정, 가정 | `docs/STATUS.md` | 결정 직후 |
| 기술·구조 결정 | `docs/adr/` | 결정 직후 |
| 작업별 계획과 진행 경과 | `docs/plans/<이슈>-<이름>.md` | 계획 시, 단계 완료마다 |
| 사용자에게 보이는 변경 | `CHANGELOG.md` `[Unreleased]` | 커밋 시 |
| 반복된 실수, 환경 함정 | `AGENTS.md` Gotchas | 발견 즉시 |

5. **세션**: 시작하면 STATUS.md와 진행 중 계획 문서로 현재 위치를 한두 줄 브리핑한다. 열린 `P0` 이슈가 있으면 모드와 관계없이 그것을 먼저 꺼낸다. 작업 단위가 끝나면 `/wrap`을 제안한다. "이어서 하자", "다음"은 `/next`와 같다.
6. **단계 문서를 읽는다**: 단계에 들어가거나 그 단계의 작업을 시작할 때 아래 표의 해당 파일을 먼저 읽고 따른다. 브랜치·커밋·PR·병합 전에는 `git-flow.md`를 따른다.

## 흐름

```
0 초기화 → 1 아이디어·PRD → 2 설계 → 3 계획 → [4 구현 ⇄ 5 검증] → 6 릴리즈 → 7 회고
             ↑ 큰 새 기능                 ↑________ 다음 마일스톤 ____________|
             |____________ 유지보수 모드 (버그 분류 → 수정 → PATCH) ←_______|
```

0~2단계는 처음 한 번, 3~7단계는 마일스톤마다 반복한다. 첫 릴리즈 뒤로는 개발 모드와 유지보수 모드를 오간다. 끝은 정하지 않는다.

| 단계 | 상세 절차 | 게이트 (승인 조건) |
|---|---|---|
| 0 초기화 | [process/00-init.md](process/00-init.md) | 저장소 준비, STATUS 단계 1 |
| 1 아이디어 구체화·PRD | [process/01-idea-prd.md](process/01-idea-prd.md) | MVP 범위·비목표 확정, PRD 승인 |
| 2 설계 (스택·개발 환경·릴리즈 방식) | [process/02-design.md](process/02-design.md) | 기술 선택 ADR, 설계 문서 승인 |
| 3 계획 (Walking Skeleton, 이슈 분해) | [process/03-plan.md](process/03-plan.md) | 마일스톤·이슈 승인 |
| 4 구현 (이슈마다 반복) | [process/04-build.md](process/04-build.md) | 이슈별 계획 승인, DoD |
| 5 검증 | [process/05-verify.md](process/05-verify.md) | 마일스톤 DoD, 사람 확인 |
| 6 릴리즈 | [process/06-release.md](process/06-release.md) | 버전·배포 승인 |
| 7 운영·회고, 다음 방향, 종료 | [process/07-retro.md](process/07-retro.md) | 다음 방향 선택 |
| 유지보수 모드 (버그 처리) | [process/maintenance.md](process/maintenance.md) | 우선순위 승인 |
| Git 작업 흐름, main 보호 | [process/git-flow.md](process/git-flow.md) | 병합 승인 |
| 기존 프로젝트 도입 | [process/adopt.md](process/adopt.md) | — |

## 명령어

| 명령 | 용도 |
|---|---|
| `/kickoff [아이디어]` | 새 프로젝트 시작 (0단계 점검 → 1단계 인터뷰) |
| `/next` | 현재 상태 파악 후 다음 행동 제안 |
| `/plan <이슈>` | 구현 계획 작성 |
| `/adr <주제>` | 결정 기록 작성 |
| `/review` | 변경 사항을 DoD 기준으로 점검 |
| `/fix <이슈 또는 증상>` | 버그 분류 후 수정 루프 |
| `/wrap` | 세션 마무리: 상태·기록 갱신, 커밋 제안 |
| `/adopt [템플릿 경로]` | 빈 폴더·기존 프로젝트에 이 구조 적용 (플러그인, [process/adopt.md](process/adopt.md)) |

| 아키텍처 개요 / 기능 설계 | `docs/architecture/overview.md`, `<기능>.md` | 구조 변경 시 갱신 |

| 문서 템플릿 | `docs/templates/` | — |
