# 1단계: 아이디어 → spec

목적: 사람의 아이디어를 **누구의 어떤 문제를 어떻게 푸는지**가 분명하고, 기능마다 검증 가능한 동작(시나리오)이 적힌 spec(`docs/SPEC.md`)으로 만든다. 어떻게 구현할지는 아직 다루지 않는다. 판단은 사람이 하고, Claude는 묻고 초안을 쓴다.

관행: Lean Canvas, 5 Whys, Jobs-to-be-Done, 사용자 스토리, MoSCoW, Given-When-Then

## 1-1. 아이디어 인터뷰 (Lean Canvas 기반)

Claude는 먼저 사람이 준 설명(프롬프트, 첨부 문서)에서 아래 항목을 최대한 추출하고, **비어 있거나 모호한 항목만** 아래 순서로 한 주제씩 질문한다.

- 설명이 충분하면 인터뷰 없이 요약을 보여주고 확인만 받은 뒤 1-2로 넘어간다.
- 설명이 한 줄뿐이면 처음부터 인터뷰한다.

1. **문제** — 어떤 상황에서 무엇이 불편한가? 답이 해결책 형태("~하는 앱")로 나오면 **5 Whys**로 그 밑의 문제를 찾는다.
2. **사용자** — 누가 그 문제를 가장 절실하게 겪는가? (얼리어답터 한 부류로 좁힌다)
3. **현재 대안** — 지금은 어떻게 해결하고 있고, 무엇이 부족한가?
4. **해야 할 일(JTBD)** — "~할 때, ~하고 싶다, 그래야 ~할 수 있다" 형식으로 정리
5. **가치 제안** — 기존 대안 대비 한 문장으로 말하는 차별점
6. **해결책 핵심 기능** — 가치 제안을 증명하는 최소 기능 3개 이내
7. **성공 지표** — 잘 되고 있다는 것을 무엇으로 알 수 있는가?
8. **제약** — 일정, 플랫폼, 비용, 사용할 수 있는 기술

사람이 답을 모르면 Claude가 2~3개 후보와 추천안을 제시하고, 고른 것은 `[제안]`으로 남긴다.

**기록 위치**: full은 `docs/templates/idea-brief.md`를 `docs/idea-brief.md`로 복사해 인터뷰 메모로 쓴다(이후 갱신하지 않는 참고 문서). **lite일 때**: 브리프 파일을 만들지 않고 답을 바로 SPEC.md 1절(개요)과 2절 기능 목록에 쓴다.

**규모 정하기**: 인터뷰 끝에 Claude가 규모(lite / full)를 추천하고 [승인 요청]한다. 결과는 SPEC.md 머리 표의 "규모"와 STATUS.md에 적는다. 아래 "규모: lite와 full"을 따른다.

## 규모: lite와 full

규모는 **문서의 양과 승인 왕복**만 바꾼다. spec이 유일한 기준이라는 것, 판단은 사람이 한다는 것, 훅·커버리지 검사·main 보호·릴리즈 게이트는 둘 다 같다.

**판정** — 모두 해당하면 lite, 하나라도 아니면 full. lite로 시작해도 조건이 깨지면 Claude가 full 전환을 [제안]한다.
- 배포 단위(앱)가 하나다
- 사용자가 본인 또는 소수다
- 결제·개인정보·외부에 공개되는 서비스가 없다
- MVP가 한두 주 안에 끝날 크기다

**템플릿을 쓰지 말아야 할 때** — 한 번 쓰고 버릴 스크립트, 하루짜리 실험, 테스트할 로직이 없는 것. 인터뷰에서 이렇게 보이면 Claude는 그 사실을 알리고, 템플릿 없이 진행할지 [질문]한다.

| 단계 | full | lite |
|---|---|---|
| 1 | 브리프(`docs/idea-brief.md`) → SPEC.md | 브리프 없이 바로 짧은 SPEC.md. 시나리오는 테스트를 쓸 기능에만 |
| 2 | 항목별 ADR + 설계 문서 | ADR 하나("스택·개발 환경·릴리즈" 묶음), 설계 문서 없음, 단일 앱 구조 |
| 1·2 게이트 | 따로 승인 | **한 번에 승인** — spec 승인 요청에 스택 추천을 함께 올린다 |
| 3 | 마일스톤·GitHub 이슈 | `docs/plans/mvp.md` 체크리스트(기능 ID만), 이슈는 선택 |
| 4 | 이슈마다 계획 문서·승인 | 계획 승인은 처음 한 번(mvp.md), 이후 항목 단위로 진행 |
| 5 | 마일스톤마다 spec 대조 | MVP 끝에 한 번 |
| 7 | `docs/retros/`에 회고 | STATUS.md 세션 로그에 KPT 세 줄 |

**lite에서 두지 않는 파일** — 규모가 lite로 승인되면 `/kickoff`가 목록을 보여주고 [승인 요청]한 뒤 지운다. 나중에 필요하면(첫 장애, full 전환) 템플릿 저장소에서 가져온다.
- `docs/idea-brief.md`(내용은 SPEC.md로 옮긴 뒤), `docs/architecture/`, `docs/runbooks/`, `docs/postmortems/`, `docs/retros/`
- `docs/templates/`의 `design-doc.md`·`runbook.md`·`postmortem.md`·`retrospective.md`·`idea-brief.md`
- `apps/`, `packages/`, `tools/`(모노레포 구조), `CONTRIBUTING.md`
- 함께 고칠 것: AGENTS.md "저장소 구조"·"아키텍처 제약"을 단일 앱 기준으로, `docs/README.md` 표에서 지운 폴더 행, `.template-version`에 `scale=lite`

**lite → full 전환**: 옮길 문서는 없다. SPEC.md에 빠진 절(비기능·성공 지표)과 나머지 기능의 시나리오를 채우고, 위에서 지운 파일을 템플릿에서 가져오며, `.template-version`의 `scale`을 `full`로 바꾼다. 기능 ID는 그대로 쓴다.

## 1-2. spec 작성

`docs/SPEC.md`(뼈대가 이미 있다)를 채운다.

1. Claude가 초안을 쓴다: 개요(문제·사용자·목표·비목표·플랫폼), 기능 소절(제목 줄 `### F-NN 이름 — 우선순위 · 상태`, 사용자 스토리, 시나리오), 비기능 요구사항, 성공 지표, 마일스톤 초안.
   - 시나리오는 Given-When-Then, 기능마다 정상 경로 하나 + 실패·경계 경로 최소 하나. Then은 관찰 가능한 결과만.
   - 사람이 말한 것은 `[확정]`, Claude가 채운 것은 `[제안]`, 정해야 하는데 정보가 없는 것은 `[미정]`.
   - 써 봐야 정답을 아는 기능(화면의 느낌, 조작감, 처음 써 보는 외부 API·기기)은 억지로 시나리오를 짓지 말고 제목에 `[탐색]`을 붙여 "알아낼 것"과 "상한"만 적는다.
   - 자동화할 수 없는 시나리오는 `(수동)`.
2. 사람에게는 **판단이 필요한 것만** 보여준다: `[제안]` 목록(추천과 이유), `[미정]` 목록(선택지와 추천), MVP 범위(Must)와 비목표. 한 번에 1~4개씩 묻는다.
3. 사람이 확인하면 `[제안]`을 `[확정]`으로 바꾸거나 고친다. 기능 상태는 모두 `Planned`, 8절 변경 이력에 "최초 승인"을 남긴다. `[미정]`은 남아 있어도 된다 — 그 기능은 착수할 때 묻는다.

spec은 승인 뒤에도 **계속 갱신하는 유일한 기준**이다. 범위·동작이 바뀌면 같은 커밋/PR에서 SPEC.md를 먼저 고치고 변경 이력에 남긴다. 범위에 넣지 않은 요청은 7절 백로그에 모은다.

**lite일 때**: 개요는 몇 줄, 기능은 MVP만. 시나리오는 **테스트를 쓸 기능에만**(분기, 데이터 변환, 파일·네트워크 처리가 있는 로직) 정상 하나 + 실패 하나. UI 배치나 단순 표시 기능은 소절 제목과 `(수동)` 한 줄이면 된다. 3·4절은 비워 두어도 된다. 2단계 스택 추천(ADR 초안)을 함께 만들어 아래 게이트에서 한 번에 승인받는다.

**게이트 [승인 요청]**: Must 기능마다 시나리오(또는 `[탐색]`)가 있고, `[제안]`이 남아 있지 않으며, 비목표가 적혀 있고, 사람이 승인했다(lite는 스택 ADR도 함께). → [02-design.md](02-design.md) (lite는 2단계 게이트를 건너뛰고 [03-plan.md](03-plan.md))
