# 3단계: 계획

관행: Walking Skeleton, 수직 슬라이스, MVP, Definition of Ready

| Claude | 사람 |
|---|---|
| 마일스톤·이슈 분해 초안 | 우선순위 조정, 승인 |
| 승인 후 GitHub 마일스톤·이슈 생성 | — |

1. 첫 마일스톤은 **Walking Skeleton**: 모든 계층(UI → 로직 → 저장 → 빌드 → 배포)을 최소 기능으로 관통하는 실행 가능한 뼈대. 이때 함께 붙인다:
   - 개발 환경: ADR "개발 환경과 도구"대로 워크스페이스·버전 고정·린트·테스트 설정을 만든다. 깨끗한 환경(새 clone)에서 AGENTS.md의 명령만으로 설치 → 테스트 → 빌드가 통과하는지 확인한다.
   - 자동 검증 훅: `.claude/hooks/checks.env`에 포매터·린터·타입 체크·단위 테스트 명령을 AGENTS.md 명령과 같게 채운다. 일부러 린트 오류와 실패 테스트를 만들어 훅이 잡는지 확인한 뒤 되돌린다 ([guardrails.md](guardrails.md)).
   - CI: `.github/workflows/ci.yml`의 명령을 AGENTS.md 명령과 같게 채운다.
   - 릴리즈: 2단계 ADR에서 정한 방식대로 릴리즈 워크플로를 만들고, 테스트 태그(예: `v0.0.1`)로 한 번 끝까지 돌려 본다 (태그 push는 [승인 요청]). 확인이 끝난 테스트 릴리즈는 삭제할지 pre-release로 남길지 [질문]한다.
   - main 보호: CI가 동작하면 보호 규칙을 켤지 [질문]한다 ([git-flow.md](git-flow.md) "main 보호").
2. 이후 마일스톤은 **수직 슬라이스**(사용자가 체감하는 기능 하나를 끝까지)로 나눈다. 계층별 분할("DB 먼저 다 하고 UI")은 피한다.
3. 이슈 하나 = PR 하나 = 세션 하나 정도의 크기로 맞춘다(이슈 템플릿 사용). spec의 기능을 시나리오 묶음으로 나눠 이슈를 만든다 — 이슈 본문에는 **구현할 시나리오 ID**(`F-01.1, F-01.2`)만 적고 동작을 다시 쓰지 않는다. 제목은 `[F-01] …`, 기능과 무관한 작업(설정·정리 등)은 `[chore] …`.
   - `[탐색]` 기능은 탐색 이슈(`[F-05][탐색] …`, 알아낼 것과 상한)와 본 구현 이슈를 따로 만든다. 본 구현 이슈는 탐색이 끝나 시나리오가 생긴 뒤에 착수한다.
4. 지금 착수할 이슈만 상세 계획(`/plan`)을 쓴다. 먼 미래 이슈는 제목 수준으로 둔다.

**Definition of Ready (착수 가능 조건)**
- [ ] 구현할 시나리오가 spec에 Given-When-Then으로 있고, 실패·경계 시나리오가 하나 이상 있다
- [ ] 그 기능에 `[미정]`·`[제안]`이 남아 있지 않다 (남아 있으면 착수 전에 [질문])
- [ ] 의존하는 결정(ADR)이 끝났다
- [ ] 한 세션(수 시간) 안에 끝낼 크기다

**lite일 때**: 마일스톤·이슈 대신 `docs/plans/mvp.md` 체크리스트 하나로 계획한다. 항목은 기능 ID와 이름만(`- [ ] F-02 내보내기`) — 내용은 SPEC.md에 있다. 이슈를 쓸 때만 제목 접두어 규칙을 적용한다.
