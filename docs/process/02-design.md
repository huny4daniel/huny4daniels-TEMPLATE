## 추천 기준

2단계의 모든 추천(스택, 구조, 개발 환경, 릴리즈 방식)은 다음 순서로 정한다.

1. **spec에 근거해 후보를 거른다** — 목적·가치 제안, 대상 사용자와 사용 환경(OS·기기·브라우저), 비기능 요구사항(성능, 오프라인, 보안, 배포 대상), 제약(일정, 비용, 사람이 아는 기술)을 만족하지 못하는 선택지는 제외한다.
2. **남은 후보 중에서는 표준적인 것을 고른다** — 다음을 갖춘 것을 우선한다.
   - 널리 쓰이고(커뮤니티·생태계 규모, 사례) 활발히 유지보수되는 것
   - 기능·사용자·앱이 늘어도 구조를 갈아엎지 않아도 되는 확장성 (모노레포에 `apps/`·`packages/`가 추가되는 상황 포함)
   - 문서가 풍부해 사람과 코딩 에이전트 모두 다루기 쉬운 것
   - 같은 스택의 다른 도구들과 함께 쓰는 조합이 일반적인 것
3. **추천에는 근거를 붙인다** — 각 추천마다 "spec의 어떤 항목(기능·NF ID) 때문에 이것이 맞는가"와 "다른 표준 후보 대신 이것을 고른 이유"를 한두 줄로 적는다. 니치하거나 새로 나온 도구는 spec 요구가 그것을 필요로 할 때만 제안하고, 그 이유를 밝힌다.
4. **추천 형태는 후보 상황에 따라 다르다**

| 상황 | 제시 방식 |
|---|---|
| 기준을 통과한 표준이 사실상 하나 (예: Android 앱 → Kotlin + Gradle) | 단일 추천 + 근거 → 승인만 받는다 |
| 기준을 통과한 후보가 여럿이고 장단점이 분명함 (예: 데스크톱 UI로 PyQt vs Tauri vs Electron) | **선택지 2~3개**를 장단점 표(spec 항목과 연결)로 보여주고, 무엇을 중시하느냐에 따라 달라지는 점을 짚은 뒤 추천안을 하나 표시한다 → 사람이 고른다 |
| 후보 간 차이가 사람의 우선순위·취향에만 달려 있음 (예: 개발 속도 vs 실행 성능) | 추천을 정하지 않고, 먼저 어떤 가치를 우선할지 [질문]한 다음 그 답으로 추천한다 |

사용자 전역 설정(예: `~/.claude/CLAUDE.md`)에 선호 도구나 표준이 있으면, 위 기준을 통과하는 한 그것을 추천안으로 삼는다.

## 진행

1. Claude가 결정이 필요한 항목 목록을 먼저 보여준다 (언어·프레임워크, 저장 방식, 대상 플랫폼, 개발 환경, 배포 형태·릴리즈 방식 등).
   - **릴리즈 방식**은 프로젝트마다 다르므로 고정하지 않고 여기서 고른다. 예: GitHub Release에 설치 파일·APK 첨부 / 앱스토어·패키지 저장소 배포 / 서버 배포 / 수동 배포. 태그 트리거 여부, 빌드 도구, 결과물 형식, 이전 릴리즈 정리 방식을 함께 정해 ADR로 남긴다.
   - **개발 환경**은 항목마다 따로 묻지 않고, 정해진 스택의 표준 도구 **조합을 한 묶음으로** 추천한다: 런타임 버전과 고정 방법, 패키지·의존성 관리, 워크스페이스 도구, 린터·포매터, 타입 체크, 테스트 프레임워크. (예 — Python: 3.12, uv workspaces, ruff, mypy, pytest, `.python-version` / TypeScript: Node LTS, pnpm workspaces, Turborepo, ESLint, Prettier, tsc, Vitest, `.nvmrc`) 묶음 안에서도 장단점이 분명한 항목은 떼어 선택지로 묻는다. 사람은 전체 승인하거나 바꿀 것만 말한다. 결과는 ADR "개발 환경과 도구" 하나로 남긴다.
2. 항목별로 대안 비교 → 사람 선택 → ADR 작성(`/adr`)을 반복한다.
3. `docs/architecture/overview.md` 작성(템플릿 `docs/templates/design-doc.md`): 시스템 컨텍스트, 구성 요소(= apps/packages 분할), 데이터 모델, 주요 흐름. 다이어그램은 C4의 Context / Container 수준(Mermaid)이면 충분하다.
4. 모노레포 분할 원칙
   - 배포 단위 = `apps/` 하나. 단일 앱 프로젝트도 같은 구조를 쓴다 (`apps/` 하나, `packages/` 비어 있음).
   - 두 곳 이상에서 쓰면 `packages/`로 승격. 처음부터 쪼개지 않는다 (YAGNI).
   - 의존 방향은 `apps → packages`만 허용.
5. 스택과 개발 환경이 정해지면 AGENTS.md를 채운다: 스택·명령어 표(설치, 실행, 테스트, 린트, 타입 체크, 빌드), **아키텍처 제약**(overview·ADR 중 코드에서 어기기 쉬운 것, 근거 ADR 링크), **코딩 컨벤션**(언어 표준 가이드 + 린터가 못 잡는 것만, 각 한 줄). 길어지면 줄인다. README의 시작하기 명령도 채우고, CONTRIBUTING.md의 `{{릴리즈 ADR 링크}}`를 릴리즈 ADR 링크로 바꾼다. 워크스페이스 설정과 버전 고정 파일은 3단계 Walking Skeleton에서 만든다.

## 스택별 모노레포 도구 (표준 선택지)

| 스택 | 워크스페이스 | 태스크 러너 |
|---|---|---|
| JavaScript/TypeScript | pnpm workspaces (`pnpm-workspace.yaml`) | Turborepo 또는 Nx |
| Python | uv workspaces (루트 `pyproject.toml`의 `[tool.uv.workspace]`) | `uv run`, Makefile/justfile |
| Android/Kotlin/JVM | Gradle 멀티 프로젝트 (`settings.gradle.kts`) | Gradle |
| 혼합 | 언어별 워크스페이스를 각 앱 폴더에 두고 | 루트 Makefile/justfile로 통합 |

**lite일 때**: 추천 기준은 같다. 결정은 ADR 하나("스택·개발 환경·릴리즈")로 묶고 설계 문서(`docs/architecture/`)는 만들지 않는다. 모노레포 대신 단일 앱 구조로 두고 AGENTS.md "저장소 구조"를 그에 맞게 쓴다. 이 ADR은 1단계 spec 승인 요청에 함께 올려 한 번에 승인받는다([01-idea-spec.md](01-idea-spec.md) "규모").
