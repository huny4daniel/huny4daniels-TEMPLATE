# 유지보수 모드 (버그 처리)

첫 릴리즈 이후 오류 수정이 주된 일이 되면 이 모드로 진행한다. 이슈 트리아지, 회귀 테스트, 핫픽스 같은 일반적인 유지보수 관행을 따른다. 명령: `/fix <이슈 또는 증상>`

## 1. 트리아지 (분류)

새 이슈나 버그 제보가 들어오면 Claude가 다음을 하고 사람은 우선순위만 승인한다.

1. 재현 시도 → 재현 절차·환경을 이슈에 정리. 재현되지 않으면 필요한 정보를 [요청]한다.
2. 분류: 버그(`bug`) / 기능 요청(`enhancement`) / 질문·중복·의도된 동작(닫기 제안)
3. 우선순위 제안:

| 라벨 | 기준 | 처리 |
|---|---|---|
| `P0` | 실행 불가, 데이터 손실, 보안 문제, 대부분의 사용자 영향 | 진행 중 작업을 멈추고 즉시 수정 → 핫픽스 릴리즈 |
| `P1` | 주요 기능 장애, 우회 방법이 어려움 | 다음 작업으로 수정 |
| `P2` | 일부 기능 문제, 우회 가능 | 모아서 처리 |
| `P3` | 표시·문구 등 사소한 문제 | 여유 있을 때 |

기능 요청은 바로 구현하지 않고 PRD의 "11. 백로그"에 `- (날짜, 출처 #이슈) 요청 한 줄`로 모았다가 개발 모드(1 또는 3단계)에서 다룬다. 버그 수정이 의도된 동작(spec)을 바꾸게 되면 spec을 먼저 고친다.

**lite일 때**: 백로그는 브리프의 "나중에" 절이다.

## 2. 수정 루프

```
재현 → 실패하는 테스트 → 원인 분석 → 수정 → 검증 → 커밋 → 기록
```

1. **재현**: 증상을 확실히 재현한다. 최신 `main`에서 `fix/<이슈번호>-<짧은-이름>` 브랜치를 만든다.
2. **실패하는 테스트(회귀 테스트)**: 버그를 재현하는 자동 테스트를 먼저 만든다. 자동화가 어려운 경우(UI 등)는 수동 확인 절차를 이슈에 적는다.
3. **원인 분석**: 증상이 아니라 근본 원인을 찾는다. 같은 원인의 다른 증상이 있는지도 확인한다.
4. **수정**: 원인만 고친다. 관련 없는 리팩터링을 섞지 않는다.
   - 작은 버그: 계획 문서 없이 진행하고, 원인과 수정 내용을 이슈 댓글·커밋에 남긴다.
   - 수정 범위가 크거나 구조적 원인: 4단계처럼 `docs/plans/`에 계획을 쓰고 [승인 요청]한다. 구조 변경이면 ADR도 쓴다.
5. **검증**: 새 테스트와 전체 테스트·린트·빌드 통과. 사람이 확인해야 하면 확인 방법을 [요청]한다.
6. **커밋·기록**: CHANGELOG `[Unreleased]`의 `Fixed`에 기록, PR(`Closes #<이슈번호>`) → CI 통과 → 병합 [승인 요청] ([git-flow.md](git-flow.md)), STATUS.md 갱신.

## 3. 릴리즈

- **P0**: 수정 즉시 PATCH 릴리즈(핫픽스, [06-release.md](06-release.md)). 사용자 영향이 있었으면 Postmortem을 쓴다.
- **P1~P3**: 수정이 몇 개 모이거나 일정 기간이 지나면 Claude가 PATCH 릴리즈를 [제안]한다.

## 4. 모드 전환

- 유지보수 모드에서 `/next`는 열린 버그를 P0 → P3, 같은 등급은 오래된 순으로 제안한다. 열린 P0는 모드와 관계없이 최우선이다.
- 기능 요청이 쌓이거나 열린 P0·P1이 없으면 Claude가 개발 모드(새 마일스톤, [03-plan.md](03-plan.md)) 전환을 [제안]한다.
