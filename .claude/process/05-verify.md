# 5단계: 검증

관행: 테스트 피라미드, CI, spec 대조(converge)

- **테스트 피라미드**: 단위 테스트 다수 > 통합 테스트 일부 > E2E/수동 소수.
- **CI**: PR마다 설치 → 린트 → 타입 체크 → 테스트 → 빌드. 실패한 PR은 병합하지 않는다. 모노레포에서는 변경된 패키지와 그 의존자만 테스트하는 것이 일반적이다 (Turborepo/Nx의 affected, 또는 경로 필터).
- **리뷰**: 작성한 세션과 다른 세션에서 `/review`를 돌리면 더 객관적이다.
- **통합 실행 확인**: 마일스톤 끝에 Claude가 앱을 처음부터 실행해 마일스톤의 사용자 시나리오 전체를 이어서 돌려 본다 (이슈별로는 통과했어도 함께 쓸 때 깨지는 것을 찾기 위함). 결과를 기록한다.
- **사람 확인 — 한 번에**: 마일스톤 동안 STATUS.md "사람 확인 대기"에 모인 항목과 통합 실행에서 Claude가 확인하지 못한 것을 **하나의 체크리스트로 한 번에 [요청]**한다. 항목마다 한 줄(무엇을 / 어떻게 / 기대 결과)로 쓰고 순서대로 따라 할 수 있게 묶는다. 결과를 받으면 통과한 것은 목록에서 지우고, 실패는 이슈(lite는 `mvp.md` 항목)로 만든다.
## spec 대조

마일스톤이 spec대로 만들어졌는지 확인한다. 두 겹이다 — **존재는 기계가, 의미는 Claude가** 본다.

1. **기계 검사**: `bash .claude/hooks/spec-coverage.sh`가 통과한다(Done 기능의 자동 시나리오마다 테스트에 ID가 있고, 사람 확인 전 판단이 남지 않음). `SPEC_TEST_GLOB`가 비어 있으면 이 스크립트는 검사 없이 0으로 끝나므로 **통과로 보지 않는다** — 시험 위치를 채우고 다시 돌린다. `--summary`로 이 마일스톤의 Must 기능이 모두 `Done`인지 본다.
2. **의미 대조**: Claude가 이 마일스톤의 기능마다 —
   - 시나리오 → 대응 테스트: 테스트가 Given·When·Then을 실제로 검증하는가(ID만 달린 빈 테스트, 다른 것을 검사하는 테스트를 찾는다).
   - 시나리오 → 코드: 실패·경계 시나리오의 처리가 구현돼 있는가.
   - 코드 → spec: 사용자에게 보이는 동작 중 spec에 없는 것이 있는가.
   - 작성한 세션과 다른 세션에서 하면 더 객관적이다.
3. **결과를 분류해 처리한다** — 코드는 여기서 고치지 않고 할 일만 만든다.

| 분류 | 처리 |
|---|---|
| 시나리오는 있는데 구현·테스트가 부족 | 이슈(lite는 `mvp.md` 항목) 추가 |
| 테스트가 시나리오와 다른 것을 검사 | 테스트 수정 항목 추가 |
| 코드에만 있는 동작 | 사람의 판단이다 — spec에 시나리오를 `[제안]`으로 추가할지, 코드를 없앨지 [질문] |
| spec이 실제로 정한 것과 다름 | SPEC.md 갱신 + 변경 이력 |

결과는 분류 표 형식으로 계획 문서나 STATUS.md 세션 로그에 남긴다. 할 일이 생기면 4단계로 돌아가 처리하고, 다시 대조한다 — **할 일이 0이 될 때까지** 4 ⇄ 5를 반복한다.

**lite일 때**: MVP가 끝났을 때 한 번 한다. 결과는 `mvp.md`에 항목으로 붙인다.

**게이트 [승인 요청]**: 마일스톤의 모든 이슈가 DoD를 만족하고, spec 대조에서 남은 할 일이 0이며, 사람 확인을 마쳤다("사람 확인 대기"가 비었다). 사람 확인 요청과 이 게이트는 한 번에 물어도 된다 — 확인이 모두 통과하면 그대로 승인으로 본다. → [06-release.md](06-release.md)
