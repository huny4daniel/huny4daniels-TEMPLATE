# 4단계: 구현 (이슈마다 반복)

관행: Explore → Plan → Code → Commit (Anthropic Claude Code 권장 워크플로), TDD

```
Explore → Plan → [승인] → Code → Verify → Commit → 기록
```

1. **다음 이슈 선택** — spec 요약(`bash .claude/hooks/spec-coverage.sh --summary`) 기준으로, 현재 마일스톤에서 판단(`[미정]`·`[제안]`)이 남지 않은 Must 기능의 열린 이슈 중 의존성이 풀린 것, 같으면 번호 순. 판단이 남은 기능은 착수 전에 그 판단부터 묻는다. Claude가 제안하고 사람이 확인한다(/next와 같은 기준).
2. **Explore** — 관련 문서·코드를 읽기만 한다.
3. **Plan** — `docs/plans/<이슈>-<이름>.md` 작성(`/plan`) → **[승인 요청]**. 승인 전에는 코드를 쓰지 않는다.
4. **Code** — 이슈 브랜치에서 계획 단위로 구현. 계획이 참조한 **시나리오마다 실패하는 테스트부터** 만든다(TDD: 실패 → 구현 → 통과). 테스트 이름이나 주석에 시나리오 ID를 남긴다(예: `test_f03_1_save_ok`, `# F-03.1`). 형식은 언어 관례를 따른다. `(수동)` 시나리오는 계획 문서의 "사람 확인" 목록으로 보낸다.
5. **Verify** — 세 단계로 확인한다.
   1. **자동 검사**: 린트는 파일 수정 직후, 타입 체크·단위 테스트는 응답 종료 시 훅이 자동으로 돌린다. 그와 별개로 계획 문서의 자동 검증 명령(통합 테스트, 빌드 등)을 실행한다.
   2. **Claude가 직접 실행해 확인**: 실행 가능한 앱이면 실제로 띄워 계획 문서의 수동 확인 시나리오를 Claude가 먼저 돌려 본다 — CLI는 명령 실행 결과, 웹은 브라우저·스크린샷, 데스크톱·모바일은 실행 로그와 가능한 경우 스크린샷(`/run`). 발견한 문제는 사람에게 넘기기 전에 고친다.
   3. **사람 확인**: Claude가 볼 수 없는 것(실제 기기, 체감 품질·사용성, 외부 계정이 필요한 흐름)만 **[요청]**으로 넘긴다. 무엇을, 어떤 순서로, 무엇을 기대하며 볼지 구체적으로 적고, Claude가 이미 확인한 항목은 표시한다.
6. **Commit** — 논리 단위로 커밋, CHANGELOG 갱신 → PR 생성 → CI 통과 확인 → 병합 [승인 요청] ([git-flow.md](git-flow.md)).
7. **기록** — 계획 문서 진행 기록과 상태 Done, **spec 환류**(기능의 시나리오가 모두 구현·테스트됐으면 SPEC.md 기능 제목의 상태를 `Done`으로 — `--summary`의 "시험 없음"에 그 기능의 ID가 없어야 한다, 구현 중 시나리오·범위가 바뀌었으면 SPEC.md 본문과 변경 이력도 같은 PR에서), STATUS.md 갱신 → 다음 이슈 **[제안]**.

구현 중 spec에 없던 결정이 필요해지면 PROCESS.md의 **판단의 경계**로 나눈다. 사람이 할 판단(보이는 동작·범위·트레이드오프)이면 SPEC.md에 `[미정]` 또는 `[제안]`으로 적고 **[질문]**한 뒤, 답을 받을 때까지 그 부분은 진행하지 않고 다른 `[확정]` 작업을 한다. Claude가 정해도 되는 것(표준이 분명함, 내부 구현)이면 진행하고 근거를 남긴다. 방향이 틀어지면 덧칠하지 않고 되돌린 뒤 계획을 고친다.

**lite일 때**: 같다. 이슈별 계획 문서 대신 `docs/plans/mvp.md` 항목 단위로 진행하고, 기능이 끝나면 `mvp.md` 체크와 SPEC.md 상태 `Done`을 함께 바꾼다.

## 탐색 경로 — 써 봐야 아는 기능

SPEC.md 기능 제목에 `[탐색]`이 붙은 기능(화면의 느낌, 조작감, 처음 써 보는 외부 API·기기)은 spec을 먼저 쓰지 않고 만들어 보며 알아낸다. 판단은 여전히 사람이 한다 — 탐색은 판단에 필요한 정보를 얻는 과정이다.

1. **시작**: 기능 소절에 "알아낼 것"(질문 목록)과 "상한"(예: 세션 하나)이 있는지 확인한다. 없으면 [질문]한다. `spike/<F-ID>-<짧은-이름>` 브랜치에서 프로토타입을 만든다. 테스트·린트 훅은 그대로 돌지만, `[탐색]` 기능은 `Done`이 될 수 없다(spec 커버리지 검사).
2. **보여주기**: 상한에 닿거나 질문에 답할 만큼 알게 되면 멈추고, 알아낸 것을 사람에게 보여준다(실행 결과·스크린샷·선택지별 장단점). 체감이 필요하면 직접 써 보도록 [요청]한다.
3. **끝내기** — 셋 중 하나를 [승인 요청]한다:
   - **spec으로**: 알게 된 것으로 시나리오를 쓰고(`[제안]` → 사람 확인 → `[확정]`) `[탐색]`을 뗀다. 본 구현은 일반 경로(이슈·계획·TDD)로 한다. **프로토타입 브랜치는 병합하지 않는다** — 코드를 재사용하더라도 시나리오와 테스트를 먼저 붙인 뒤 본 구현 브랜치로 옮긴다.
   - **버리기**: 기능 상태를 `Dropped`로.
   - **계속**: 상한을 늘린다(이유를 변경 이력에).
4. 어느 쪽이든 SPEC.md 변경 이력에 한 줄 남긴다. 판단 근거가 기술적이면 ADR도 쓴다. spike 브랜치는 결정 후 지운다.

## 세션 운영

- 한 세션 = 한 작업. 작업이 바뀌면 `/clear`. 이어서 할 일은 계획 문서에 적어두면 다음 세션이 이어받는다.
- 같은 실수를 두 번 하면 AGENTS.md Gotchas에 추가한다.
- 독립적인 작업은 git worktree로 분리해 병렬 세션을 돌릴 수 있다.

## Definition of Done (완료 조건)

- [ ] 계획이 참조한 시나리오를 모두 만족하고, 자동 시나리오마다 ID가 달린 테스트가 있다
- [ ] 테스트 추가/수정, 전체 테스트 통과
- [ ] 린트·타입 체크·빌드 통과
- [ ] 필요한 문서(ADR, README, CHANGELOG) 갱신
- [ ] 리뷰(`/review` 또는 사람) 완료
