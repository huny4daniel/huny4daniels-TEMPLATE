description: 버그 트리아지 후 수정 루프 진행 (유지보수 모드)
argument-hint: <이슈 번호 또는 증상 설명>
---

대상: $ARGUMENTS

docs/process/maintenance.md 절차와 docs/PROCESS.md 협업 규칙을 따른다.

1. **트리아지**
   - 이슈 번호면 `gh issue view`로 읽는다. 증상 설명이면 중복 이슈를 검색하고, 없으면 버그 보고 템플릿 형식으로 이슈 생성을 [제안]한다.
   - 재현을 시도한다. 재현되지 않으면 필요한 정보(재현 절차, 로그, 환경)를 [요청]하고 멈춘다.
   - 버그 / 기능 요청 / 의도된 동작을 판단하고, 버그면 P0~P3를 근거와 함께 제안해 [승인 요청]한다. 저장소에 `P0`~`P3` 라벨이 없으면 승인 후 만든다.
   - 기능 요청이면 수정하지 않고 PRD 백로그 추가를 제안한다.
2. **수정 루프** (우선순위 승인 후)
   - 최신 `main`에서 `fix/<이슈번호>-<짧은-이름>` 브랜치를 만든다.
   - 버그를 재현하는 실패 테스트를 먼저 작성하고 실패를 확인한다. 자동화가 어려우면 수동 확인 절차를 이슈에 적는다.
   - 근본 원인을 찾아 설명한다. 같은 원인의 다른 증상이 있는지 확인한다.
   - 수정 범위가 크거나 구조적 원인이면 멈추고 docs/plans/ 계획 작성으로 전환해 [승인 요청]한다.
   - 원인만 고친다. 관련 없는 변경을 섞지 않는다.
   - 새 테스트와 전체 테스트·린트·빌드를 실행한다. 사람이 봐야 하면 확인 방법을 [요청]한다.
3. **기록**
   - CHANGELOG `[Unreleased]`의 `Fixed`에 추가, 원인과 수정 요약을 이슈에 남기고 커밋한다. PR(`Closes #<이슈번호>`)을 만들고 CI 통과를 확인한 뒤 병합을 [승인 요청]한다 (docs/process/git-flow.md).
   - docs/STATUS.md 갱신. P0였으면 핫픽스 릴리즈와 Postmortem 작성을 [제안]한다. 아니면 쌓인 수정 수를 보고 PATCH 릴리즈 시점인지 판단해 [제안]한다.
