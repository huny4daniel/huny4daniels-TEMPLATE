description: 현재 변경 사항을 spec과 Definition of Done 기준으로 점검
---

1. `git diff`(스테이징 포함), 관련 계획 문서(docs/plans/), 계획이 참조한 docs/SPEC.md의 기능 소절을 읽는다.
2. 다음을 점검하고 항목별로 통과/미통과와 근거를 보고한다:
   - **spec 대조(시나리오별)**: 계획이 참조한 시나리오마다 — 코드가 Given·When·Then대로 동작하는가, 대응 테스트(ID가 달린)가 그 시나리오를 실제로 검증하는가. 시나리오별 통과/미통과로 보고한다
   - `(수동)` 표시가 맞는가: 체감·실기기·외부 계정처럼 정말 자동화할 수 없는 것만 `(수동)`이어야 한다. 입력→출력이 정해진 로직이 `(수동)`이면 테스트로 바꾸도록 지적한다 — 커버리지 검사를 피하는 통로가 되지 않게
   - 버그·엣지 케이스·오류 처리 누락
   - 테스트 추가 여부, 그리고 AGENTS.md의 테스트·린트·타입 체크 명령 실제 실행 결과
   - AGENTS.md의 아키텍처 제약(의존 방향 등)·코딩 컨벤션 위반
   - 계획 문서의 "Claude 실행 확인" 시나리오를 실제로 돌렸는지와 결과
   - 이번 작업에서 반복된 실수가 있으면 AGENTS.md Gotchas 추가 제안
   - ADR / CHANGELOG / README 갱신 필요 여부
   - 요구사항 ID 사슬: 바뀐 코드가 계획 문서의 F-ID에 속하는가(범위 밖 변경은 없는가), 계획이 참조하는 시나리오 ID마다 대응 테스트(이름·주석의 ID)가 있는가, 브랜치의 PR·이슈에 F-ID(또는 chore)가 있는가
   - spec 갱신 필요 여부: 이번 변경이 SPEC.md와 다르게 동작하거나 spec에 없는 동작을 추가했는가. 그렇다면 SPEC.md 시나리오·기능 상태·변경 이력이 같은 변경에 들어 있는가. 사람이 할 판단(보이는 동작·범위)을 Claude가 혼자 정한 흔적은 없는가 — 있으면 `[제안]`으로 되돌려 확인받도록 지적한다
   - 비밀 값 포함 여부
3. 수정은 하지 않고 발견 사항만 심각도 순으로 나열한다.
